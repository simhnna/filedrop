# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm dev          # dev server (localhost:5173)
pnpm build        # production build → dist/
pnpm preview      # serve dist/ locally (also uses SPA fallback)
pnpm check        # svelte-check + tsc — run this before committing
pnpm test         # vitest (src/**/*.test.ts)
cd cli && go test ./...
```

Both test suites read shared vectors from `testdata/` to keep the web app and CLI byte-compatible: `pake.json` (PAKE shares/MACs from fixed seeds, SDP fingerprint canonicalisation) and `compat.json` (room codes, file keys, `have` decoding). The expected PAKE values are generated by the Go side — after an intentional protocol change run `go test ./internal/pake -update` in `cli/`, then make the TS side match.

### Licenses

`pnpm build` writes `dist/licenses.txt` (Vite's `build.license`) covering everything bundled; the footer links to it. The CLI embeds `cli/internal/licenses/licenses.txt` and prints it via `filedrop licenses`. That file is generated and committed: after changing Go dependencies (or `LICENSE`) run `go generate ./internal/licenses` in `cli/`; CI fails if it's stale. The generator takes the union of dependencies across linux/darwin/windows and lists the Go standard library with `golang.org/x/*` (identical license text).

## Stack

Svelte 5 (runes) + TypeScript + Vite, no SvelteKit, no CSS framework. Package manager is **pnpm**.

## Architecture

### Signaling

The y-webrtc WebSocket hub at `wss://connect.hannaweb.eu` is an **external codebase** — do not modify files here to change its behaviour. If signaling server changes are needed, produce a prompt for the operator to run in that repo.

The hub implements y-webrtc pub/sub: clients `subscribe` to a topic, `publish` messages that are broadcast to all other subscribers on that topic. Each room uses topic `filedrop:<first two words of roomId>` (see Room name generation). All signaling messages include `from: peerId` so peers can filter out their own echoes, and `to: peerId` on directed messages (offer/answer/ice).

### Connection lifecycle (`src/lib/peer.ts`)

Both peers re-announce every 4 seconds until connected — this resolves the race where one side subscribes before the other. The **host** (whoever created the room) creates the WebRTC offer the first time it sees a peer announce. `isHost` is determined by `sessionStorage.getItem('host:<roomId>')`, set when navigating from the Landing page.

The host always accepts multiple peers: `Room.svelte` keeps exactly one unconnected "listening" slot (a `FiledropPeer` + `FileTransferManager` pair) and creates a new one whenever a slot connects or disconnects. Peers only connect to the host (star topology), not to each other.

Two RTCDataChannels are created by the host and received by the peer via `ondatachannel`:
- `control` — reliable/ordered, carries JSON messages
- `data` — reliable/ordered, carries binary chunks; flow-controlled via `bufferedAmountLowThreshold` (pause at 1 MB, resume at 256 KB)

### Authentication (`src/lib/pake.ts`, `cli/internal/pake`)

Every connection runs a CPace-style PAKE over ristretto255 on the control channel before anything else is accepted:
1. On control-channel open, each side derives a generator from `SHA-512(lv("filedrop-cpace-v1", secret, hostFp, peerFp))` (RFC 9496 element derivation), where `hostFp`/`peerFp` are the canonicalised `a=fingerprint` lines of the host's and peer's SDP. It sends `{ type: 'pake', share }`.
2. On the other share, it derives `isk = SHA-512(lv("filedrop-cpace-isk", hostFp, peerFp, hostShare, peerShare, K))` and sends `{ type: 'pake-confirm', mac: HMAC-SHA256(isk, "filedrop-confirm-<own role>") }`.
3. Once the other side's MAC verifies, the peer emits `connected`. Control and data messages before that are dropped.

Binding the DTLS fingerprints into the PAKE means a signaling server that swaps SDP fingerprints (MITM) can't complete the exchange without guessing the secret, one guess per connection. Each side answers only one share per connection, and auth times out after 15 s. On failure `authFailed` fires: a peer shows "Verification failed"; the host replaces the slot and, after 5 failures (`MAX_AUTH_FAILURES`), stops listening ("Room locked"). **The TS and Go implementations must stay byte-for-byte compatible.**

### Transfer protocol (`src/lib/transfer.ts`)

**The receiver drives the transfer.** Flow:

1. Sender calls `addFile()` → sends `manifest` control message. Each file has a per-connection numeric `id` (used in the chunk header) and a fingerprint `key` = first 128 bits of SHA-256 over `name\nsize\nlastModifiedMs`, hex (`fileKey()`; the Go CLI computes the same). The receiver looks the key up in the `ReceiveStore`: unknown → offer; paused → resume silently; complete/downloaded → reply `have` with every chunk (the sender marks it sent); busy with another peer → ignore.
2. Receiver calls `onFileOffered` callback → UI decides to `acceptFile()` or `rejectFile()` (which sends `{ type: 'reject', fileId }` so the sender stops waiting on that peer)
3. `acceptFile()` claims the key in the `ReceiveStore`, then sends `have` with current chunk bitmap (empty for new, partial for resumed)
4. Sender receives `have`, computes missing ranges via `invertRanges()`, sends only those chunks
5. Each chunk: 8-byte header (`[4B fileId][4B chunkIdx]`) + payload on the data channel
6. Receiver writes chunk to OPFS at `chunkIdx * CHUNK_SIZE` offset, updates in-memory bitmap

The `have` message uses compact range pairs `[[start,end],...]`; switches to base64 bitmap when range count > 500 (degenerate fragmentation).

### Receive storage (`src/lib/storage.ts`)

`Room.svelte` opens one `ReceiveStore` per room and shares it with every peer slot's `FileTransferManager`. Entries are keyed by fingerprint key and owned by at most one manager at a time (`claim()` / `release()`); when a slot closes, its unfinished files are released and shown as "paused" until any peer offers the same key again.

Chunks land in the browser's Origin Private File System under `filedrop-<roomId>/`, per file:
- `<key>.bin` — raw file data (pre-allocated to full size via `truncate`)
- `<key>.bitmap` — received-chunk bitmap (Uint8Array, ~4 KB per 2 GB file)
- `<key>.meta.json` — `FileInfo` for cross-session restore
- `<key>.done` — marker written after the user downloads the file (the other three are deleted), so re-offers on reconnect are ignored

The `FileSystemWritableFileStream` is kept open and checkpointed (closed + reopened) every 512 chunks so data is flushed to disk. On load, the store restores every `.meta.json` entry: partial files show as paused, complete-but-not-downloaded ones as ready to download. Falls back to in-memory chunks if OPFS is unavailable.

On every open, a sweep over all `filedrop-*` directories deletes entries untouched for 7 days and removes empty room directories.

### Routing (`src/App.svelte`)

SPA history-API routing. `/` → Landing, `/about` → About (intro + FAQ), `/cli` → Cli (install + usage), `/r/#<roomId>` → Room; any other path falls back to Landing. The room code lives in the URL **fragment** so it never reaches a server: fragments aren't sent in requests, server/CDN logs or Referer headers. `App.svelte` owns `path` and `hash` state and passes a `navigate(to)` function as a prop to both `Landing` and `Room`; `popstate` and `hashchange` keep them in sync. `Room` is wrapped in `{#key roomId}` so switching rooms remounts it.

The Vite config sets `appType: 'spa'` for dev/preview; **production servers must serve `index.html` for all routes** (at least `/r/`). The CLI prints `/r/#<roomId>` links and `filedrop recv` accepts either a bare code or a pasted link.

### Download mode

`Room.svelte` tracks `downloadMode: 'auto' | 'manual'`, shown to the user as the "Ask before receiving" toggle (on = `manual`, the default). In `auto` mode, `acceptFile()` is called immediately inside `onFileOffered`; switching to `auto` also accepts any offers still pending. In `manual` mode the UI shows Accept/Reject buttons per file. The transfer manager itself is mode-agnostic — it always calls `onFileOffered` and waits.

### Sender progress

Outgoing files live in `Room.svelte` with `sent: Record<slotId, number | null>` — `null` while a peer hasn't accepted, otherwise the chunks it has (seeded from its first `have`, so resumes start at the right percentage). Entries are removed when a peer rejects or disconnects. Every newly connected peer is offered all files shared so far. The row shows combined progress across peers that accepted, plus "Sent to x of n peers" when more than one is connected.

### Text transfer

Sent as `{ type: 'text', content: string }` on the control channel. No chunking, no OPFS. Received texts appear as copy/dismiss cards in the Room UI.

### Room name generation (`src/lib/roomName.ts`)

4 words from the EFF short word list (1,283 words, `src/lib/wordlist.ts`) using rejection-sampling from `crypto.getRandomValues` to avoid modulo bias. The Go CLI (`cli/internal/roomname`) generates names the same way.

`parseRoomId()` splits the name: the first two words are the signaling topic (`filedrop:<w1>-<w2>`), the remaining words are the PAKE secret, which is never sent anywhere. The CLI's `pake.SplitRoom()` must match.

`normalizeRoomCode()` (CLI: `roomname.Normalize()`) is the single entry point for user-supplied codes: it strips a pasted link down to its fragment, lowercases, splits on dashes/whitespace and rejects anything that isn't exactly 4 wordlist words. `App.svelte` runs it on `/r/#…` URLs, canonicalises the hash via `replaceState`, and shows Landing with the error and the code prefilled when it's invalid.
